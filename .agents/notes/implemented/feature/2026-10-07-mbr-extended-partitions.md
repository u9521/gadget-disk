# Agent Note: MBR 扩展分区、逻辑分区与显式扩展容器

Status: implemented

## Problem

MBR 首扇区只有 **4 个分区项槽位**，因此 `layout: "mbr"` 下最多只能建 4 个分区。
要放第 5 个及以后的分区，必须占用其中一个槽位作为**扩展分区**容器，其内部再以
**EBR**（Extended Boot Record）链描述**逻辑分区**。容器还有第二种用途：**先预留
一片空间，以后再往里放逻辑分区**。

改动之前，`MbrPartitionType::Extended`（`0x05`）**已经存在于类型空间**
（`byte()` / `as_wire()` / `label()` / `parse()` / `presets()` 五处齐全），
出现在 WebUI 的类型预设与文档的类型表里——**但写入侧没有任何实现**：

- `write_mbr` 只写 `446 + i*16` 的四个主分区项，不生成 EBR、不填充扩展区间；
- `grep -rn "EBR\|0x05" crates/` 除类型定义外**零命中**；
- 读取侧 `parse_mbr_sector` 只跳过 `0xEE`（GPT 保护分区），把 `0x05` 当作**普通
  数据分区**列出来。

因此选中「扩展分区」的用户得到的是：一块**占着主分区槽位、容量被白白吃掉、里面
什么都挂不上**的空壳，而 UI 还把它显示成一个可挂载的分区（挂上去必然失败）。
**这是静默失败，不是「尚未实现」**——所以本次任务不能只做新增功能，必须先修掉
既有的错误行为，否则用户仍会走到空壳那条路。

## Proposal

### 1. 位置由求解器决定，存在性与容量由用户表达

这是本设计**最容易做过头**的地方，边界必须写清楚：

| 维度 | 由谁决定 | 理由 |
|---|---|---|
| 容器的**位置与对齐** | **求解器** | 由逻辑分区链的排布推出（每个 EBR 紧邻其分区、逐段对齐），用户手填必然与链的实际跨度冲突 |
| 容器的**存在性与容量** | **用户** | 「先预留一片空间」是独立且合理的诉求；把存在性也收走会让「1 主 + 1 空容器」无从表达 |

`PartitionSpec::kind` 为三态：

```rust
pub enum PartitionKind { Primary, Logical, Extended }
```

- **不引入 `extended: bool` 字段**：那会让「是不是容器」有两个可能矛盾的来源
  （`kind` 与 `extended`）。`kind` 一个字段就够，且与前端「归属」下拉的三项一一
  对应。这条正交性判断同时是**不用 `mbr_type == Extended` 表达归属**的理由——
  把容器类型与成员归属混为一谈，正是导致上述 bug 的思维。
- `MbrPartitionType::Extended` 从 `presets()` 移除（UI 预设同步移除）；
  `parse("mbr:extended")` **保留**，以便存量请求不报错。
- 容器的**类型字节恒为 `0x05`**，仍不是用户可选的「类型」：容器行**忽略**其
  `mbr_type`。反过来，非容器行填了 `mbr:extended` 会被拒绝并**指引改用归属**
  （只说「类型非法」，用户不知道该怎么办）。

### 2. 容器的存在性 = `有逻辑分区 || 有显式容器行`

```rust
let has_extended = has_logical || explicit_extended.is_some();
```

槽位计数同步为 `primaries + usize::from(has_extended)`。**空容器同样占一个槽位**
——这是「3 主 + 1 空容器」用满 4 槽、「4 主 + 1 容器」需要 5 槽被拒的原因。

### 3. 容量的两个来源：规则必须唯一

| 情况 | 容器区间由谁决定 |
|---|---|
| 有逻辑分区 | **EBR 链推导**，显式容器行的 `size_bytes` 被**忽略** |
| 空容器（无逻辑分区） | 用户声明的 `size_bytes`（`0` = 占满剩余） |

不允许同时采纳两个来源：那会让「容器多大」有两个互相矛盾的答案，而用户在界面上
看不出哪个生效。该规则在代码注释、`docs/disk-image-format.md`、`docs/webui.md` 与
UI 提示文案里**一致陈述**。

### 4. 空容器的容量下限：1 MiB（`MIN_EXTENDED_BYTES`）

容器里没有文件系统，只需放得下 EBR（一个扇区）与至少一个扇区的逻辑分区。取**一个
对齐单位**而不是一个扇区，是因为逻辑分区必须**对齐**：小于一个对齐单位的容器放不下
任何合法逻辑分区，建出来注定是个用不上的空壳。

`resolve_sizes` 拒绝显式低于下限的容器容量；下限与 `ALIGNMENT_BYTES` 的关系由一个
`const { assert!(…) }` 钉住（写成编译期断言，否则 clippy 会判
`assertions_on_constants`）。

### 5. 空间记账不重复扣减

`create::build` 里 MBR 的可用区间按**逻辑分区数**扣 `SECTOR_BYTES + ALIGNMENT_BYTES`
（每个 EBR 及其对齐余量）。**空容器不产生 EBR，因此不扣这两项**；容器自身的容量走
`resolve_sizes` 的常规记账。两处都扣会让明明够用的容量被报成放不下。

「占满剩余空间」的名额由**分区与容器共用**：容器的容量确实占用镜像空间，共用一套
记账才能让「谁拿剩余」有唯一答案（两者都填 `0` 会被拒绝，而不是按某个隐式顺序分配）。

### 6. 布局求解为纯函数

```rust
pub fn resolve_mbr_layout(specs, sizes, total_sectors, alignment) -> Result<MbrPlan>
```

`MbrPlan` 给出主分区槽位、扩展区间、EBR 位置与每个分区的绝对 LBA。**位置与容量的
全部计算都在求解器里**，写入器只负责把结果编成字节——这样「会不会重叠」这类问题
能在主机上用纯函数穷举测试，而不必写坏真实镜像。

关键规则：

- 主分区先占槽位 `0..n_primary`，**扩展容器紧随其后**占一个槽位，因此
  `n_primary + usize::from(has_extended) <= 4`；
- 每个逻辑分区**前面紧邻一个 EBR 扇区**（EBR 占 1 个扇区，不与分区重叠）；
- **扩展区间覆盖整条链**：从首个 EBR 到最后一个逻辑分区结束；
- **无逻辑分区且无显式容器行时输出与旧实现逐字节相同**（回归底线，由测试钉住）。

### 7. 逻辑分区序号从 5 起

Linux 惯例：主分区占 1–4，逻辑分区从 **5** 起，**即使主分区没占满 1–4 也是这样**。
`PartitionEntry::index` 的职责是「与内核 `loopNpM` 的 `M` 一致」，按「紧随主分区
之后」编号会让 UI 序号与设备名错位。扩展分区容器本身**不占序号**（它不是可挂载分区）。

### 8. 读取侧遍历 EBR 链，并把相对偏移换算成绝对

`parse_ebr_chain(first_ebr_lba, &mut dyn FnMut(u32) -> Option<Box<[u8;512]>>)` 是纯
函数（读取器注入），因此可在主机测试。

**EBR 里两项的 `starting_lba` 都是相对本 EBR 的偏移，而首扇区的项是绝对 LBA。**
混用会得到错得离谱的偏移，且镜像在 Host 上看起来仍然「合法」。因此本函数在解析后
**立刻换算成绝对 LBA 再返回**，使调用方拿到的语义与主分区一致（也才能直接用作
`LOOP_SET_STATUS64` 的 `lo_offset`）。

**防护是必需的，不是防御性编程**：损坏的镜像可以给出任意链指针。实际生效的两道是
**链长上限**（`MAX_EBR_CHAIN` = 64）与**链指针溢出保护**（`checked_add`）。无防护的
遍历会在 `su` 域的 `gadgetdisk serve` 里死循环，表现为「界面卡死」而非明确报错。
停止时如实返回已解析的部分。

**空容器要读得回来**：`parse_mbr_sector` 产出一个 `index = 0` 的条目
（`kind()` 据此返回 `Extended`），由 `read_partitions` 决定去留：

- EBR 链**非空** → **移除**容器条目（否则同一区间既显示为容器又显示为里面的分区，
  用户会以为容量被算了两遍）；
- EBR 链**为空** → **保留**（用户建了一个预留用的扩展分区，回头看详情时不该发现
  它消失了）。

`index == 0` 是容器唯一不可能与真实分区混淆的取值（真实分区从 1 起），由测试钉住。

### 9. 两处必须一并修正的既有缺陷

否则启用逻辑分区后会立刻出错：

- **`create::build` 的区间配对**：原本 `tables.iter().zip(&specs)` 按**位置**配对。
  `tables` 按内核序号排列（主分区在前、逻辑分区在后），而 `specs` 是用户填写顺序
  （逻辑分区可能夹在中间），于是**逻辑分区的文件系统规格被套到别的主分区上**，
  格式化落到错误区间（表现为引导扇区内容错乱，实测复现）。
  修法：`PartitionTable` 增加 `spec_index` 字段，调用方按它配对。
- **`verify_formatted` 传 `u64::MAX` 作为区间上界**：`fscommon::StreamSlice` 按
  `size = end - start` 计算读写窗口，传 `u64::MAX` 会得到一个远超镜像实际长度的
  窗口，读到的内容不一定是刚写进去的那一份，**校验结果不再可信**。修法：传真实
  `end`。

### 10. 容量与校验

- `create::build` 的 MBR 可用区间**每个逻辑分区额外扣一个 EBR 扇区加对齐余量**。
  不扣就是高估，会让 `resolve_sizes` 放行一个写不进去的请求。
- `verify_mbr` 的 `used_entries` 比对**按「主分区数 + 是否存在扩展容器」**，不是
  `tables.len()`——逻辑分区住在 EBR 里，不在首扇区，用后者会永远不等。
- `parse_mbr_sector` 不再把 `0x05` 当普通分区列出，`mbr_type_label` 补上
  `0x05 => "Extended"`。

### 11. UI：名称字段不渲染、容器不渲染类型选择器、逻辑分区缩进

三条都出自同一条原则：**渲染一个禁用的控件比不渲染更糟**——用户会以为自己可以填、
只是被挡住了。

- MBR 下名称字段**整个不渲染**（该布局没有分区名字段）；
- 容器行**不渲染类型与文件系统选择器**（没有数据区），只显示容量 + 一句说明；
- 容器标题**绝不显示数字**：后端把容器读回来时 `index` 正是 `0`，显示「分区 0」
  会让用户以为存在一个序号为 0 的设备。

渲染顺序为「主分区 → 扩展容器 → 逻辑分区」，逻辑分区包进
`.partition-logical-group` 缩进分组。**但 DOM id 一律用行在 `createPartitions` 里的
原始下标**：`readPartitionRow`/`syncPartitionRows` 都按原始下标读写，用渲染序号会让
重绘后每行的输入串到别的行上。

### 12. 接口

- REST：`partitions[].kind`（`primary` 缺省 / `logical` / `extended`）；
  `capabilities` 增 `mbr_max_primary`，`max_partitions.mbr` 改为**总数**上界（3 + 64）。
- CLI：`--partition SIZE/GPT/MBR/NAME/FS/KIND`，**KIND 放末尾**以免破坏既有 5 段语法。
  主分区不下发 `kind`，老请求形状逐字节不变。
- 列表应答的 `index` / `kind` 按内核序号给出，`offset_bytes` 一律是绝对偏移。

## Alternatives considered

**A. 把 `mbr:extended` 实现成「用户可选、手填容器容量」的普通类型。**
否决：容器区间与逻辑分区区间互相约束，用户填的容量与逻辑分区总和必然经常矛盾。
让用户维护一个**可被推出**的值，只会制造需要额外校验与报错的输入面。

**B. 把容器的存在性也从用户手里收走（只在有逻辑分区时隐式产生）。**
否决：这是把「位置不能手填」这个**正确结论过度套用**了。真正由逻辑分区推出的只有
**位置与对齐，不是存在性**；按 B 的做法，「1 主 + 1 个空扩展容器」这个完全合理的
组合建不出来，用户只剩两个坏选择：建一个逻辑分区占位（日后删除要重建表，预留失去
意义），或改用别的分区工具（正是本模块要取代的事）。

**C. 用一个 `extended: bool` 字段表达容器。**
会把「这一行是不是容器」变成两个来源（`kind` 与 `extended`）可能互相矛盾的状态。
`kind` 已经是一个完备的三态枚举，再加一个布尔值只会制造需要额外校验的不一致。否决。

**D. 空容器的下限取「一个扇区」。**
规格上够（EBR 就是一个扇区），但容器起点之后紧邻的 EBR 与其后的逻辑分区都要落在
**对齐边界**上，一个扇区的容器放不下任何合法逻辑分区。取一个对齐单位让「低于下限」
直接等价于「建了也没用」。否决。

**E. 保留 `parse_mbr_sector` 跳过 `0x05`，让读取侧完全忽略容器。**
这样空容器在详情里**不可见**。对「预留」这个用途来说，用户建完就看不到自己建了
什么，属于我们一贯要避免的静默失败。否决。

**F. 引入 `mbrman` crate 处理 MBR/EBR。**
源码实测后否决（`mbrman 0.6.1`）：它写 `00 00 00` 而非本仓库的 `FE FF FF` CHS
哨兵、`read_from` 拒绝全零镜像（`InvalidSignature`）、把 `0xEE` 当普通占用项，且在
30 个依赖节点的树上增加 25 个节点。本仓库既有风格就是手写磁盘/内核结构，EBR 又比
GPT 简单得多。

**G. 用「扩展分区 + 段数组」建模逻辑分区（如某些工具的做法）。**
否决：与 MBR/EBR 的实际磁盘格式不符，读回来仍要重新解释，凭空多一层映射。

**H. 只在读取侧支持 EBR（能读不能写）。**
否决：用户的核心诉求就是**创建**含逻辑分区的镜像；且读取侧支持会立刻暴露
「写出来的 `0x05` 是空壳」这个既有缺陷，反而更需要写入侧的正确实现。

**I. 沿用「4 主」上限，只把 `mbr:extended` 从 UI 移除。**
这确实能消除静默失败，是最低限度修复。但逻辑分区是 MBR 的既定能力，移除类型却不给
替代路径等于削减功能。故采纳完整方案，同时把「移除可选类型」作为其中一步。

## Acceptance criteria

1. 无逻辑分区且无显式容器行时，`resolve_mbr_layout` 输出与旧写入器**逐字节相同**
   （回归底线）；
2. `3 主 + 2 逻辑` 的镜像：首扇区第 4 槽为 `0x05` 且覆盖整条链，两个 EBR 各就位，
   序号为 `1,2,3,5,6`；
3. 「1 主 + 1 空扩展容器」能建出来；Host 上 `fdisk -l` 看到 `0x05` 项，**且没有 EBR**；
4. 「3 主 + 1 空容器」合法；「4 主 + 1 容器」被拒且报错说明容器占一个槽位；两个容器
   行被拒；
5. 空容器的区间精确等于声明的容量（不是对齐单位、不是整盘）；有逻辑分区时，显式
   容器行的容量被忽略、区间覆盖整条 EBR 链；
6. 容器行不能被格式化；只有容器的表被拒（Host 上什么都挂不上）；
7. `read_partitions` 读回的逻辑分区 `start_lba` **等于写入侧报告的绝对 LBA**
   （已验证：故意把相对偏移当绝对值会让该断言失败，报 `写 34817，读 1`）；
   读回来时空容器仍可见，`index` 为 `0`、`kind` 为 `extended`；
8. 逻辑分区的 FAT32 引导扇区通过 `verify_formatted`，且能被 loop 适配器解析出与
   创建时一致的 `offset_bytes`；
9. `parse_ebr_chain` 对**链指针溢出**、**超 64 节点（对抗性不重复链）**、
   **截断扇区**、**缺 `55AA`**、**中间空项** 五种畸形输入均能终止且不 panic；
   环检测保留但不作为验收项（见 `## Risks`——它不可达）；
10. GPT/raw 下的 `logical` 与 `extended` 被拒绝；
11. `mbr:extended` 不在 UI 预设里，把它当**分区类型**提交被拒绝并指引改用归属；
12. MBR 下 DOM 里不存在名称 input；容器行不渲染类型/文件系统选择器、不显示数字；
    逻辑分区在缩进分组内渲染；
13. 老请求（不带 `kind`）的 REST 契约与 CLI 命令行**逐字节不变**；
14. `gd-check` 6 项全绿、`gd-test --all` 全绿、治理门禁通过、Android 交叉编译通过；
15. **AVD 实测通过**：MBR 槽 1 为 `0x05` 且起始 LBA 等于首个 EBR（`133120`）；
    两个 EBR 的相对偏移换算正确（`+1` 指向逻辑分区、链尾项全零）；
    REST 读回 `index 1/5/6` 且 `kind` 正确；按分区 5 的绝对偏移 `attach-loop`
    挂为 `vfat` 并可读写，改挂分区 6 得到全新空文件系统（区间互不重叠）。

## Risks

- **新增回归测试必须做「改回 bug 版本应当失败」的注入验证，且断言必须双向。**
  本条来自三处具体教训：环检测测试去掉环检测后照样通过（该分支实际不可达）；分区
  规格配对测试因规格同质、顺序巧合而恒真；空容器读回测试只断言「找得到容器」，
  于是 `retain` 极性写反导致主分区消失时仍然通过。**规格同质、顺序巧合、`retain`
  极性写反**是最容易让测试退化成恒真断言的三点；只断言「要找的东西在」不够，还要
  断言「不该消失的东西还在」。
- **逻辑分区与空容器的真机行为待复核。** 主机侧验证了「创建 → 读表 → 解析出绝对
  `offset_bytes`」全链路；AVD（x86_64 / Android 17）进一步验证了**真机挂载路径**
  （按逻辑分区的绝对偏移 `attach-loop` 成功挂为 `vfat` 并可读写，两区间互不重叠），
  以及空容器的创建与读回。**arm64 真机仍属待验证假设**
  （[docs/roadmap.md](../../../../docs/roadmap.md) 待验证假设 #18 / #22）。
  风险点在于分区表解析完全由本仓库保证（partscan 已移除，内核不参与 MBR 解析），
  因此若 EBR 解释有偏差，内核不会独立发现。缓解：纯函数穷举测试 + 写后读回的往返
  断言 + AVD 实测字节核对。
- **内核对「有 `0x05`、无 EBR」的分区表的行为未在真机验证**：Linux 通常会接受并
  列出容器，但真机挂载行为待复核（路线图 #22）。
- **容器容量被忽略的规则容易被误读**：用户为容器行填了 64 MiB，又放了逻辑分区，
  结果容器变成别的值。规则必须同时出现在 UI 提示、`docs/protocol.md` 与
  `docs/disk-image-format.md` 里，否则会以「我填了却变了」的形式回到对话里。
- **`index == 0` 作为容器标记**是一个隐式约定：若哪天分区序号改成从 0 开始，容器就
  会被当成主分区。有一条测试（`mbr_parser_index_zero_is_the_only_container_marker`）
  同时钉住两侧取值。
- **容器的槽位约束有两个实现**：core 的 `validate` 与 `resolve_mbr_layout` 都算了
  `needed_slots`。二者的输入相同（`specs`），但重复实现总有漂移风险；当前由
  `solver_container_takes_a_slot_even_when_empty` 与
  `validate_counts_container_as_a_slot_but_not_as_a_partition` 分别覆盖。
- **UI 的渲染顺序与 `createPartitions` 数组顺序不再一致**。这是有意的（顺序要匹配
  内核槽位），代价是任何新增的按位置访问都必须用原始下标。已用一条抓取**所有**
  `id` 赋值的测试守住——只查字面量的断言会漏掉改写。
- **`kind()` 与 `FIRST_LOGICAL` 里各写了一份字面量 `4`。** 这是为了绕开
  `cast_possible_truncation`（lint 看不见常量取值）与 `u32::try_from` 尚未 const
  稳定，与 `layout::SECTOR_BYTES_USIZE` 的既有做法一致。两份字面量必须与
  `MBR_MAX_PRIMARY` 保持一致——由 `entry_kind_follows_index_with_literal_boundary`
  与 `verify_mbr_index_boundary_matches_partition_kind_boundary` 两条测试守住。
- **只支持单个扩展分区。** MBR 惯例如此；若磁盘上有多个 `0x05` 项，只遍历首个指向
  的链，其余不猜测意图。异常布局下的行为是「少列分区」而非报错。
- **EFI/GPT 混合场景未覆盖。** 逻辑分区是 MBR 独有概念，GPT 下提交 `logical` 会被
  拒绝；本次不改动 GPT 路径。
- **行为变更（已接受）**：存量那些含空壳扩展分区的镜像，现在会多列出一个容器条目
  （早先被无条件跳过）。已记入 `docs/disk-image-format.md`。
