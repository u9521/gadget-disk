# 磁盘镜像格式

本文件定义镜像的磁盘布局与文件系统生成规格。所有数值均来自本机实测（crate 版本见下）或 **AVD 实测**（x86_64 / Android 17.1，见「格式化工具探测」一节），未在真机/其他操作系统验证的部分已标注。

依赖版本：`gpt` 4.1.0、`fatfs` 0.3.6、`fscommon` 0.1.1。

## 三种布局

| 布局 | 结构 | 分区数上限 | 分区名 | 默认 |
|---|---|---|---|---|
| `raw` | 无分区表；整个镜像即一个卷 | 1 | — | |
| `gpt` | GPT 分区表 + N 个分区（默认 BASIC Data，GUID `EBD0A0A2-B9E5-4433-87C0-68B6B72699C7`） | 128 | ✔（UTF-16 ≤36 码元） | ✔ |
| `mbr` | MBR 分区表 + N 个主分区（默认类型 `0x0C`） | **4** | ✘ | |

分区起始统一对齐到 **1 MiB**；同一镜像内的分区**不重叠**且按规格顺序排列。

### 分区数量与名称的布局差异（关键）

- **MBR 最多 4 个首扇区槽位**：合法组合是「4 主分区」或「N 主 + 1 个扩展分区
  容器」（N ≤ 3）。容器里可放最多 64 个逻辑分区，也可以是**空的**（预留空间）。
  超出的组合返回 `invalid_argument`，不做静默丢弃。详见
  [MBR 扩展分区与逻辑分区](#mbr-扩展分区与逻辑分区)。
- **MBR 没有分区名字段**：16 字节的分区项里没有放名字的位置，因此
  [`PartitionSpec::name`](../crates/gadgetdisk-core/src/partspec.rs) 在 MBR 下
  **不会写入镜像**，仅供 UI 展示。**UI 在 MBR 下整个不渲染名称字段**（而不是
  渲染成禁用控件）——用户填了却在 Host 上看不到属于静默失败，而一个禁用的输入框
  仍会让人以为自己可以填、只是被挡住了。
- **GPT 分区名以 UTF-16 计长**，上限 36 码元（UEFI 规定）。36 个汉字合法
  （108 字节），37 个即超限。超限**提前拒绝**，不让 `gpt` crate 静默截断。

### 分区类型：两套**互不相关**的类型空间

GPT 用 128 位类型 GUID，MBR 只用一个类型字节，**二者没有对应关系**。同一个
「FAT32」在 GPT 里是 Microsoft Basic Data 的 GUID，在 MBR 里是 `0x0C`。

曾用一个枚举同时携带两套语义，后果是 `fat32_lba` 与 `microsoft_basic` 都映射到
BASIC Data 而无法区分、只能表达 4 种类型，还需要「按布局过滤」的补丁。现在拆成
两个独立类型，线格式名一律带前缀。

**GPT 类型**（`gpt:` 前缀；自定义类型直接写 GUID 字面量）：

| 线格式名 | GUID |
|---|---|
| `gpt:microsoft_basic`（默认） | `EBD0A0A2-B9E5-4433-87C0-68B6B72699C7` |
| `gpt:efi_system` | `C12A7328-F81F-11D2-BA4B-00A0C93EC93B` |
| `gpt:microsoft_reserved` | `E3C9E316-0B5C-4DB8-817D-F92DF00215AE` |
| `gpt:windows_recovery` | `DE94BBA4-06D1-4D40-A16A-BFD50179D6AC` |
| `gpt:linux_filesystem` | `0FC63DAF-8483-4772-8E79-3D69D8477DE4` |
| `gpt:linux_swap` | `0657FD6D-A4AB-43C4-84E5-0933C84B4F4F` |
| `gpt:linux_lvm` | `E6D6D379-F507-44C2-A23C-238F2A3DF928` |
| `gpt:linux_raid` | `A19D880F-05FC-4D3B-A006-743F0F84911E` |
| `gpt:bios_boot` | `21686148-6449-6E6F-744E-656564454649` |
| `gpt:<GUID 字面量>` | 任意自定义 GUID |

**MBR 类型**（`mbr:` 前缀）：

| 线格式名 | 字节 |
|---|---|
| `mbr:fat32_lba`（默认） | `0x0C` |
| `mbr:fat32_chs` | `0x0B` |
| `mbr:fat16_lba` | `0x0E` |
| `mbr:ntfs_exfat` | `0x07` |
| `mbr:linux` | `0x83` |
| `mbr:linux_swap` | `0x82` |
| `mbr:linux_lvm` | `0x8E` |
| `mbr:efi_system` | `0xEF` |
| `mbr:0x<十六进制>` | 任意自定义字节 |

**`mbr:extended`（`0x05`）刻意不在预设里。** 容器的类型字节**恒为本值**，由写入侧
生成，不是用户可选的「分区类型」。要表达「这一行是容器」请用**归属**
（`kind: "extended"`）；要表达「放进容器里」请用 `kind: "logical"`。后端仍能解析
`mbr:extended`（存量请求不报错），但把它当**分区类型**提交会被拒绝并指引改用归属。
详见下文 [MBR 扩展分区与逻辑分区](#mbr-扩展分区与逻辑分区)。

**不带前缀的名字一律拒绝**——那正是过去两种布局混用的来源。

**默认类型随文件系统推断**（见 `create::default_types_for`）：例如 ext4 →
GPT `linux_filesystem` / MBR `0x83`；FAT32 → GPT `microsoft_basic` / `0x0C`。

> **自定义类型 GUID 已支持；自定义分区 GUID 尚不支持。** 前者只需构造
> `gpt::partition_types::Type { guid, os }`（其字段是 `pub`）；后者受限于 `gpt`
> crate——`add_partition` 与 `add_partition_at` 都硬编码 `Uuid::new_v4()`，且
> `partitions()` 只返回不可变引用，没有公开 API 可设置分区 GUID。

> **MBR 下类型字节 `0x00` 会被拒绝**：那会让分区项被判为空项而「消失」，
> 会导致用户配置的容量参数失效。

### 每分区文件系统

每个分区可**独立**选择文件系统，或选择**不格式化**（只写分区表）：

- REST：`partitions[].filesystem`，缺省继承全局 `filesystem`；`"none"` 表示不格式化；
- CLI：`--partition SIZE/GPT-TYPE/MBR-TYPE/NAME/FS`，`FS` 段为 `none` 即不格式化。

> **三态而非二态**：`Inherit`（未指定，用全局默认）/ `None`（显式不格式化）/
> `Some(fs)`（指定）。用 `Option<FilesystemType>` 无法区分前两者——都是 `None`
> ——会让「请求不格式化」的分区被套上全局默认并**真的被格式化**。这是实测
> 在 AVD 上暴露出来的：请求 `filesystem: "none"` 的第 3 个分区拿到了 FAT32。

### 容量分配规则

- 分区容量写 `0` 表示「占满剩余空间」；**最多一个分区**可以这样写（多个「待定」
  无法从 UI 推断出结果，故直接拒绝）。
- 指定容量总和不超出可用区间；**超出即拒绝，不静默裁剪**——静默裁剪会让用户
  以为拿到的是自己填的容量。
- 有分区表时，可用区间为「镜像容量 − 分区表首尾结构与对齐」（见 `create::build`）。
  MBR 下**每个逻辑分区还要再扣一个 EBR 扇区加对齐余量**，理由见
  [容量计算](#容量计算)。

## 分区偏移

- 对齐常量：`1 MiB = 1048576 字节 = 2048 个 512 字节扇区`。
- `raw` 布局偏移为 `0`。
- 有分区表时，**首个分区偏移必须正好是 1 MiB**（`first_lba == 2048`），后续分区按对齐规则递推。
- 分区偏移缓存持久化于 `run/offsets.json`，供 loop 挂载的 `lo_offset` 快速路径直接读取。
  **多分区后缓存记录首个分区的偏移**（兼容既有格式）；解析分区表仍是权威来源
  （`loop_adapter::resolve_offset` 在缓存缺失时回退读表）。

## GPT 生成

```rust
let cfg = gpt::GptConfig::new()
    .writable(true)
    .logical_block_size(gpt::disk::LogicalBlockSize::Lb512);
let mut disk = cfg.create_from_device(file, None)?;   // 注意：第二个参数是 Option<Uuid>
disk.add_partition("MAIN", size, gpt::partition_types::BASIC, 0, Some(2048))?;
disk.write()?;
```

**强制项**

1. **对齐参数必须显式传 `Some(2048)`**。`gpt` 的默认对齐会把分区起点放在 **LBA 34（约 17 KiB）**，未做 1 MiB 对齐，部分宿主系统与工具会判为不规范磁盘。实测对比：

   | 对齐参数 | `first_lba` | 字节偏移 |
   |---|---|---|
   | `None`（默认） | 34 | 17 KiB |
   | `Some(2048)` | 2048 | 1 MiB |
   | `Some(8)` | 40 | 20 KiB |

2. **容量上界必须用 `find_free_sectors()` 求得**，不要自行硬算，否则会与 GPT 备份头所需空间冲突。实测：4 GiB 磁盘可精确容纳 3 GiB 分区（`first_lba=34` 时 `last_lba=6291489`，即 3221225472 字节；按 1 MiB 对齐时起点变为 2048）。

   多分区时**每个分区都要重新查询空闲区间**，且要在**所有**空闲区间里挑一个放得下的。
   只看第一个区间会误判为空间不足：`find_free_sectors()` 会返回「分区项数组之后到
   第一个分区之前」这类碎片区间。若请求值超出该区间的可用长度，**返回 `no_space`
   而不是裁剪**。

3. GPT 会在磁盘首尾各写一份头部，故**可用容量小于镜像总容量**。UI 中显示的可用容量应据此计算。

4. `disk.partitions()` 返回的是 `HashMap`，**顺序不确定**。写入后必须先按 `first_lba`
   排序再编号，否则分区序号（1 起，与内核 `loopNpM` 对应）会与实际磁盘顺序不符。

## MBR 生成

构建标准首扇区（LBA 0）。每个分区项（16 字节，数组起始偏移 **446**）：

- 偏移 `+0`：引导标志 = `0x00`（非活动分区）；
- 偏移 `+1..+4`：CHS 起始 = `0xFE 0xFF 0xFF` 哨兵（表示使用 LBA 寻址）；
- 偏移 `+4`：分区类型字节（见「分区类型映射」）；
- 偏移 `+5..+8`：CHS 结束 = `0xFE 0xFF 0xFF` 哨兵；
- 偏移 `+8..+12`：起始 LBA（小端 `u32`），按 1 MiB 对齐；
- 偏移 `+12..+16`：扇区数（小端 `u32`）；
- 扇区末两字节 `510..512` = **`0x55 0xAA`**。

分区项按规格顺序写入 `446 + i*16`。**位置由写入器显式跟踪游标决定**：MBR 没有
GPT 那样的空闲区间查询，因此这里是唯一能保证分区不重叠的地方。

> MBR 的分区表容量上限受 32 位 LBA 限制（约 2 TiB）。默认 4 GiB，不触及该边界；
> 若将来允许更大容量，需切换到 GPT 或改用 LBA48 方案。

## MBR 扩展分区与逻辑分区

MBR 首扇区只有 **4 个分区项槽位**。要放第 5 个及以后的分区，必须占用其中一个槽位
作为**扩展分区**容器，其内部再以 **EBR**（Extended Boot Record）链描述**逻辑
分区**。

### 三种合法组合

| 组合 | 槽位占用 | 分区序号 |
|---|---|---|
| 4 个主分区 | 4 / 4 | 1–4 |
| 3 主 + N 逻辑 | 3 主 + 1 扩展容器 = 4 | 1–3，逻辑从 **5** 起 |
| N 主 + 1 个**空**扩展容器 | N 主 + 1 容器 = N+1 | 1–N |

**分区序号从 5 起，即使主分区没占满 1–4 也是这样**（Linux 惯例）。按「紧随主分区
之后」编号会让 UI 序号与内核 `loopNpM` 的 `M` 错位——而这正是序号字段存在的意义。

**扩展分区容器本身不占序号**：它在 `loopNpM` 里没有对应的 `M`。读取侧把它读回来时
`index` 为 `0`（真实分区从 1 起），`kind()` 据此返回 `Extended`。

### 扩展容器的两种来源

| 来源 | 何时出现 | 容量由谁决定 |
|---|---|---|
| **隐式**（自动） | 存在逻辑分区时必然有 | 求解器按 EBR 链推导 |
| **显式**（用户声明） | 用户把某行归属设为 `extended` | 用户填的容量（`0` = 占满剩余） |

用户表达「这个分区是逻辑分区」用 `kind: "logical"`；想**预留**一片空间以后再放逻辑
分区，用 `kind: "extended"` 声明一个**空容器**。无论哪种来源，容器的**位置与对齐**都
由纯函数 `partspec::resolve_mbr_layout` 推出（可穷举测试，见 `docs/testing.md`）。

> **容量有两个来源，规则必须唯一**：显式容器行与逻辑分区**同时存在**时，容器区间
> **一律由 EBR 链推导**，用户为容器行填的容量被**忽略**。否则「容器多大」会有两个
> 互相矛盾的答案。该规则在错误信息、`docs/webui.md` 与 UI 提示文案里一致陈述。

**空容器的容量下限是 1 MiB**（`MIN_EXTENDED_BYTES`，一个对齐单位）：容器里没有文件
系统，只需放得下 EBR 与一个扇区的逻辑分区；但逻辑分区必须**对齐**，因此小于一个对齐
单位的容器放不下任何合法逻辑分区，创建后将成为无法容纳任何合法逻辑分区的无效容器。`resolve_sizes` 拒绝
低于下限的容器。

**空容器不产生任何 EBR**：`MbrPlan.ebrs` 为空，扩展区间为
`[对齐边界, 对齐边界 + 容器容量)`。

> **已修正的静默失败**：早先把 `mbr:extended` 直接暴露为可选**分区类型**，但写入侧
> 不生成任何 EBR——将导致生成的扩展分区占用主分区槽位却无法挂载任何逻辑卷，造成磁盘空间
> 被无效占用。现在该类型从预设移除，容器改由**归属**表达；把 `mbr:extended` 当分区类型
> 提交会被拒绝并指引改用归属。此前早期的修复方案过度收紧了限制，未支持用户声明空容器，
> 导致无法创建诸如「1 主分区 + 1 空扩展分区」的预留结构；当前方案则合理放开该限制，
> 仅强制约束容器的位置与扇区对齐规则。

### EBR 布局（每项 16 字节，偏移同首扇区）

| 项 | 偏移 | 含义 |
|---|---|---|
| 0 | `+446` | 本 EBR 描述的**逻辑分区** |
| 1 | `+462` | **下一个 EBR**；类型 `0x05`，为空表示链尾 |
| — | `+510` | `55 AA` |

> **`starting_lba` 的语义在两处不同（最容易出错的地方）**：
>
> - 首扇区里的分区项（含**指向扩展分区的那一项**）用**绝对** LBA；
> - **EBR 里的两项都用相对本 EBR 的偏移**。
>
> 混淆两者会导致计算出的扇区偏移量严重错误，而镜像在 Host 上看起来仍然「合法」。因此读取侧在
> 解析后**立刻换算成绝对 LBA** 再返回（`parse_ebr_chain`），使调用方拿到的语义与
> 主分区一致。

### 磁盘布局

```
LBA 0            首扇区：主分区项 + 扩展分区项（0x05，覆盖整条链）
LBA 2048         主分区 1
...
LBA E1           EBR #1 ── 项0 指向 LBA E1+1，项1 指向 E2
LBA E1+1         逻辑分区 5
...
LBA E2           EBR #2 ── 项0 指向 LBA E2+1，项1 空（链尾）
LBA E2+1         逻辑分区 6
```

**空容器**（没有逻辑分区）时没有 EBR，扩展项直接覆盖用户声明的容量：

```
LBA 0            首扇区：主分区项 + 扩展分区项（0x05，起始 = 容器起点，长度 = 容量）
LBA 2048         主分区 1
LBA E1            （容器起点）← 这里**没有** EBR；区间内全是未分配空间
```

- 每个逻辑分区**前面紧邻一个 EBR 扇区**（EBR 占 1 个扇区，不与分区重叠）；
- 每个 EBR 与其后的逻辑分区都按 1 MiB 对齐；
- **扩展分区项必须覆盖整条链**：从首个 EBR 到最后一个逻辑分区结束。覆盖不全会让
  其他分区工具认为链越界；
- 空容器的起点同样对齐，且容器项的长度**必须非零**——长度为 0 的项会被读取侧判为
  空项，容器随之消失（`create::verify_mbr` 显式检查这一点）。

### 实测记录（AVD，x86_64 / Android 17）

`1 主 + 2 逻辑`、768 MiB 镜像的实测字节（`gadgetdisk create --layout mbr`）：

| 位置 | 内容 |
|---|---|
| LBA 0 槽 0 | 类型 `0x0C`，起始 `2048`，扇区 `131072` |
| LBA 0 槽 1 | 类型 `0x05`，起始 **`133120`**，扇区 `264193` |
| LBA 133120 | EBR1：项0 类型 `0x83` 相对偏移 `+1`；项1 类型 `0x05` 相对偏移 `133120` |
| LBA 266240 | EBR2：项0 类型 `0x83` 相对偏移 `+1`；项1 **全零（链尾）** |

两侧 EBR 末尾均为 `55 AA`。REST `image/partitions` 读回 `index 1/5/6`，
逻辑分区 `start_lba` 为 `133121` / `266241`（即各自 EBR + 1），`kind` 为 `logical`。

**空容器（1 主 + 1 空扩展，256 MiB 镜像）**：

| 位置 | 内容 |
|---|---|
| LBA 0 槽 0 | 类型 `0x0C`，起始 `2048`，扇区 `131072`（64 MiB） |
| LBA 0 槽 1 | 类型 `0x05`，起始 **`133120`**，扇区 `65536`（**正好 32 MiB，等于声明容量**） |
| LBA 133120 | **全零**，`+510` 也是 `00 00` —— **没有 EBR**（这正是与上一行的区别） |

REST 读回 `[{index 1, kind primary, start_lba 2048}, {index 0, kind extended,
start_lba 133120}]` —— 容器与真实分区**同时**出现。

**显式容器 + 逻辑分区共存**：声明 8 MiB 容器 + 64 MiB 逻辑分区时，首扇区容器项为
起始 `133120`、扇区 `131585`（= 64 MiB + 1 扇区 + 对齐），即**按 EBR 链推导、
声明的 8 MiB 被忽略**；EBR 项0 类型 `0x83` 相对 `+1`、项1 全零；REST 只列出
`index 1/5`（容器不再单独列出）。

**拒绝路径（实测）**：`4 主 + 1 容器` → 「需要 5 个槽位」；两个容器 → 「只能有一个
扩展分区容器」；只有容器 → 「至少要有一个主分区或逻辑分区」；GPT 下的容器 →
「扩展分区仅 MBR 支持」；容器带文件系统 → 「没有数据区，不能被格式化」；
`mbr:extended` 当类型用在非容器行 → 指引改用「归属」。

**挂载与隔离已验证（待验证假设 #18 的 AVD 部分）**：按分区 5 的绝对偏移
`attach-loop` 成功挂载为 `vfat`（`/dev/block/loop52`），写入文件后该内容落在 L1 区间
（实测字节偏移 `131047936`，位于 `68157952..135266816` 内）；随后改挂分区 6，
看到的是**全新的空文件系统**（L1 的文件不出现），证明两个逻辑分区解析到互不重叠的
区间。真机（arm64）仍待复核。

### 容量计算

MBR 的可用区间除扣头部对齐外，**每个逻辑分区还要额外扣一个 EBR 扇区加对齐余量**
（见 `create::build`）。若不扣除该开销则会导致可用空间被高估，致使 `resolve_sizes` 错误放行超出物理容量的创建请求
——而「高估」正是该处注释明令禁止的。

**空容器不扣 EBR 开销**（它不产生任何 EBR）。容器自身的容量走 `resolve_sizes` 的
常规记账，因此**不能重复扣减**：两处重复扣减会导致原本充足的容量被误判为空间不足。

「占满剩余空间」（`size_bytes = 0`）的名额由**分区与容器共用**——两者都填 `0` 会被
拒绝。容器的容量确实占用镜像空间，共用一套记账才能让「谁拿剩余」有唯一答案。

### 读取侧的防护

EBR 链是磁盘上的链表，损坏的镜像可以给出任意链指针，因此遍历必须有界。实际生效的
两道防护：

1. **链长上限**（`MAX_EBR_CHAIN` = 64）——**唯一实际可达的兜底**。对抗性输入
   （每个 EBR 都指向下一个新 LBA，既不重复也不溢出）只能靠它停下；
2. **链指针溢出保护**（`checked_add`）——偏移是**非负** `u32`，损坏的「负偏移」
   会表现为一个巨大的值，加法溢出即停止。

> **环检测（已访问 LBA 集合）按当前读取语义不可达**，作为纵深防御保留。理由：形成
> 环需要环上偏移之和为 0，而偏移都是非负 `u32`；要么全为 0（那是链尾，会先 break），
> 要么某步加法先溢出而被 (2) 拦下。
>
> 这一点值得写下来，因为**「测不到」不等于「不需要」**：一旦将来有人把偏移改成有
> 符号解析或放宽溢出检查，它就成为唯一还能拦住死循环的地方。相应地，测试只断言
> **可达的**终止原因（上限与溢出），不断言环检测本身——否则会写出「去掉环检测
> 仍然通过」的假测试（本仓库确实写出过一次）。

停止时**如实返回已解析的部分**（链上有几个能用的分区对用户仍有价值），而不是
整体报错。

**链为空时保留容器条目**：`read_partitions` 遇到 `0x05` 时先在 `parse_mbr_sector`
里产出一个 `index = 0` 的条目（`kind() == Extended`）。若 EBR 链解析出至少一个逻辑
分区，该条目被**移除**（否则同一个区间会既显示为容器又显示为里面的分区，用户会以为
容量被算了两遍）；若链为空则**保留**，即用户看到的是一块**空扩展容器**。

> **已接受的行为变更**：`parse_mbr_sector` 早先无条件跳过 `0x05`，因此**存量**那些
> 含空壳扩展分区的镜像本不会列出任何东西，现在会列出一个容器条目。此项设计旨在遵循
> 「读取解析结果与创建生成规格严格对称」的原则：用户建了一个预留用的扩展分区，回头看详情
> 时不该发现它消失了。

## 格式化：统一经 loop 设备

**格式化统一走 [`Formatter`](../crates/gadgetdisk-core/src/fs.rs) trait**：
`gadgetdisk-core` 只定义 trait 与纯逻辑（不接触平台接口），真实 `fork/exec` 在
CLI 层（[`crates/gadgetdisk-cli/src/mkfs.rs`](../crates/gadgetdisk-cli/src/mkfs.rs)）。

### 流程：逐个分区挂 loop 再格式化

分区表写好后，**逐个分区**执行：

```sh
losetup -f                                   # 取空闲 loop 设备
losetup -o <offset> --sizelimit <length> <dev> <image>
<mkfs> ... <dev>                             # 对该块设备做整设备格式化
losetup -d <dev>                             # 无条件释放
```

**为什么统一走 loop**（尽管部分工具自带 offset 选项）：

| 工具 | 偏移能力 |
|---|---|
| `mkfs.exfat` | **无**任何偏移选项 |
| `mke2fs` | `-E offset=<字节>` |
| `mkfs.fat`（dosfstools） | `--offset <扇区>` |
| 本模块自带的 `mkfs.vfat` | `--offset <扇区>` |

让每个工具各走各的偏移路径会得到「三条实现、三种失败模式」。统一经 loop 后，
偏移只在一个地方表达，各 `mkfs` 只做最简单的「对块设备格式化」，新增文件系统时
**不需要**再研究它的偏移能力。代价是每分区多一次 `losetup`/`losetup -d`。

**强制项**：

- `--sizelimit` 不可省：loop 默认把区间延伸到文件末尾，不限制的话 `mkfs` 会看到
  一个比实际分区更大的设备，写出越界的文件系统元数据。
- 每个分区**串行**处理，且**无条件释放** loop；释放失败要如实上报——残留 loop
  会让该镜像无法再被导出为 USB 设备（数据安全互斥）。

### 自带 `mkfs.vfat`：把 FAT32 做成独立二进制

设备上**不存在** `mkfs.vfat`（AVD 实测：无 dosfstools、toybox 亦无 `mkfs`），
因此模块自带一个（[`crates/gadgetdisk-mkfsvfat`](../crates/gadgetdisk-mkfsvfat/)，
安装为 `bin/mkfs.vfat`，同时提供 `mkfs.fat` 名）。

做成**独立二进制**而非进程内调用的两个理由：

1. **与其它 `mkfs` 形态一致**：`mkfs.exfat`、`mkfs.ext4` 都是外部进程，FAT32 走
   同一条路径后，格式化流程里不再有「内置特例」；
2. **可被用户直接调用**：命令行与 dosfstools 兼容，排查问题时能手工验证。

**命令行对齐 `mkfs.fat(8)`**：

| 选项 | 行为 |
|---|---|
| `DEVICE [BLOCK-COUNT]` | 位置参数；`BLOCK-COUNT` 单位 **KiB**（与 dosfstools 一致） |
| `-F FAT-SIZE` | **仅接受 32**；传 12/16 明确报错（防止底层格式化工具静默降级为非预期的 FAT12/16 格式） |
| `-n VOLUME-NAME` | 卷标（≤11 字符，超出报错） |
| `-i VOLUME-ID` | 32 位十六进制卷 ID |
| `-S` / `-s` / `-R` | 扇区大小 / 每簇扇区数 / 保留扇区数 |
| `--offset SECTOR` | 在映像指定扇区处写入（经 loop 调用时**不用**它） |
| `-v` / `--help` / `--invariant` | 详细输出 / 用法 / 固定卷 ID（便于复现测试） |
| `-V` / `--version` | 打印版本并以 0 退出。**dosfstools 没有这个选项**（其 man page 只有 `--help`），是本工具的补充：让打包与验收能核对"包里的二进制确实是这一版" |

**两个实现要点（均基于虚拟机与真机实测验证排查总结）**：

- **块设备容量必须用 `ioctl(BLKGETSIZE64)`**：对块设备 `stat(2)` 的 `st_size`
  恒为 **0**，直接用 `metadata().len()` 会把每个 loop 设备判成 0 字节。
- **`cfg` 必须同时覆盖 `android`**：Android 的 `target_os` 是 `"android"` 而非
  `"linux"`，只写 `linux` 会让块设备分支在目标平台上被整个编译掉。
- `ioctl` 的**请求参数类型随平台而异**（glibc `u64` / bionic `i32`），故不能硬编码。

### 格式化工具探测

`GET /api/v1/capabilities` 的 `mkfs` 字段如实回报本机可用的工具（含自带实现）：

```json
[ {"filesystem":"fat32","path":"/data/adb/modules/gadget-disk/bin/mkfs.vfat", ...},
  {"filesystem":"exfat","path":"/system/bin/mkfs.exfat", ...},
  {"filesystem":"ext4", "path":"/system/bin/mkfs.ext4", ...} ]
```

`path` 为 `null` 表示未找到。查找顺序：系统目录 → `PATH` → 模块自带 `bin/`
（自带实现放最后，避免覆盖设备上更原生的实现）。

> **待验证假设**：以上为 AVD（模拟器）结论，尚未在 arm64 真机验证。真机 ROM 的
> `mkfs` 集合可能与 AVD 不同（可能多、也可能少）。实现按「探测 + 分层回退」处理，
> 探测不到某个 `mkfs` 时**报错并说明**，不会静默做出错误的文件系统。

### FAT32 生成（`mkfs.vfat` 内部实现）

```rust
let slice = fscommon::StreamSlice::new(file, start_byte, end_byte)?;
fatfs::format_volume(slice, fatfs::FormatVolumeOptions::new()
    .fat_type(fatfs::FatType::Fat32)
    .volume_label(label))?;   // 卷标固定 11 字节，不足部分以空格补齐
```

这是 [`gadgetdisk-mkfsvfat`](../crates/gadgetdisk-mkfsvfat/) 的内部实现；
`gadgetdisk-core` 只保留一份**测试用**的同名实现（`cfg(test)`），
运行期格式化一律经外部 `mkfs.vfat` 进程。

**强制项**

1. **必须显式指定 `FatType::Fat32`**。`fatfs` 默认按容量自动选择，实测会**静默产生 FAT16**：

   | 分区容量 | 默认自动选择 |
   |---|---|
   | 8 MiB | Fat16 |
   | 16 MiB | Fat16 |
   | 32 MiB | Fat16 |
   | 64 MiB | Fat16 |
   | 256 MiB | Fat16 |
   | 1024 MiB | Fat32 |

   显式指定 `Fat32` 后，实测从 7 MiB 到 2 GiB 的区间均可成功格式化。

   > **FAT32 降级防御与容量下限**：当目标卷空间小于 65525 簇时，
   > `fatfs::format_volume` 即使显式指定 `FatType::Fat32` 亦会静默回退生成 FAT16 卷。
   > 实测该硬边界为 **34077184 字节（32.50 MiB）**：恰好产生 512 字节簇、共 **65525** 个
   > 簇并通过后置校验；再少一个字节即报 `Cannot select FAT type - unfortunate disk size`，
   > 32 MiB 则被校验判为 `Fat16`。为避免非预期降级，模块把 FAT32 分区下限取为
   > **33 MiB**（留出余量），并在格式化完成后执行后置校验：重新打开卷并断言
   > `fat_type() == Fat32` 且 `total_clusters() >= 65525`。

2. **用 `StreamSlice` 限定分区区间**，严禁对整盘执行格式化（否则会覆盖分区表）。在 1 MiB 偏移处格式化后，`1 MiB + 510` 处为 `55AA`，OEM 标识保留为 `MSWIN4.1`。

3. 卷标固定 11 字节。传入的卷标经 `fat::normalize_label` 规整：非 ASCII 可打印字符
   替换为 `?`（FAT 卷标是 OEM 代码页，UTF-8 中文放进去在 Host 上显示为乱码，
   不如显式替换），超出 11 字节截断，字母转大写。

### ext4 / exFAT 生成

```sh
# ext4：直接作用在文件上，带偏移
mke2fs -q -F -t ext4 -E offset=<start_bytes> -L <label> <image> <blocks>

# exFAT：无 offset 选项，先经 loop 暴露分区，再格式化块设备
losetup -o <start_bytes> <loop_dev> <image>
mkfs.exfat -L <label> <loop_dev>
losetup -d <loop_dev>
```

**注意**：`mke2fs` 与 `mkfs.exfat` 都要求目标**预先存在**且至少有一定容量
（`mke2fs` 对不存在的文件报 `does not exist and no size was specified`）。
镜像已由 `create_image` 用 `set_len` 预分配，故满足该前提。

## 容量约束

**下限是"每个分区在其所选文件系统下是否够大"，不是镜像级属性**：同一个镜像里一个
33 MiB 的 FAT32 与一个 2 MiB 的 ext4 都合法。因此这里没有"镜像最小容量"这一条。

| 约束 | 值 | 依据 |
|---|---|---|
| 单分区 FAT32 下限 | **33 MiB** | FAT32 规范要求至少 65525 个簇。宿主实测边界为 34077184 字节（32.50 MiB，恰好 65525 簇），33 MiB 是在其上留余量的取值 |
| 单分区 exFAT 下限 | **1 MiB** | **待验证假设**：宿主没有 `mkfs.exfat`，未实测。该值只用于提前拦截明显过小的分区 |
| 单分区 ext4 下限 | **2 MiB** | 宿主实测 `mke2fs` 在 1 MiB 时报 `Filesystem too small for a journal`，2 MiB 可正常建立 |
| 不格式化的分区（`filesystem=none`） | 1 MiB | 没有文件系统，只需放得下一个对齐后的分区项 |
| 扩展分区容器（空壳） | 1 MiB | 只需放得下 EBR 与至少一个扇区（`MIN_EXTENDED_BYTES`） |
| 默认容量 | **4 GiB** | 兼顾常见 U 盘场景与创建耗时 |
| 上限 | 镜像所在文件系统的可用空间 | 创建前以 `statvfs` 预检 |
| MBR 布局理论上限 | 约 2 TiB | 32 位 LBA |

> **镜像容量本身没有下限**，只拒绝 `0`（它建不出可用镜像，属参数错误而非"容量太小"）。
> 有分区表的布局要在盘首（GPT 还含盘尾）留表结构，因此"分区可用区间"小于镜像容量
> ——例如 64 MiB 的 GPT 镜像里，分区可用区间约 65011712 字节。**这不再是错误**：
> 只要该区间还能装下那个分区的文件系统就通过；装不下则返回 `size_below_minimum`，
> 并写明**第几个分区、哪个文件系统、下限与实际值**。
>
> 早先的实现把 FAT32 的 64 MiB 下限**无条件**当成镜像下限，于是「64 MiB 镜像 +
> 一个占满剩余的分区」被报成 `no_space`（界面上显示"存储空间不足"），无论那个分区
> 其实要格式化成 `none`、ext4 还是 exFAT——这是实际缺陷，不是有意为之。

> **33–48 MiB 的裸 FAT32 设备在 Linux 上可能被判成 `vfat`**：`MKFS.FAT` 判定"无分区表"
> 依据是 `st_size <= FAT32_MAX_SIZE (0xFFFFFFFF)`，而内核 `fstype` / `libblkid` 依据是
> 簇数 ≥65525。两者判据不同，故 33 MiB 的镜像在部分栈上可能显示为 `vfat` 而非 `vfat32`。
> 这一影响仅限**裸盘（raw）** 布局；Windows/macOS 的行为是**待验证假设**。

上述下限/对齐为**可调常量**，应以具名常量实现并记录依据（真机与宿主系统可能要求更严格）。

## 预分配与稀疏文件

镜像以 `set_len` 预分配。Linux 下**可能产生稀疏文件**，即「创建 4 GiB 镜像」不会立即占用 4 GiB 磁盘空间，而是在实际写入时逐步占用。

因此：

- 创建前必须用 `statvfs` 做可用空间预检；
- UI 需说明该行为，避免用户误判剩余空间；
- 无法保证写入过程不中途耗尽空间，故仍需处理 `ENOSPC`。

## 已知陷阱

**`fatfs::Dir::iter()` 会产出 `.` 与 `..` 虚拟目录项。**
递归遍历必须显式跳过上述两项，防止循环引用引发调用栈溢出。

```rust
for e in dir.iter() {
    let e = e?;
    let name = e.file_name();
    if name == "." || name == ".." { continue; }   // 必须
    // ...
}
```

**`gpt` 4.x API 与旧版差异较大**：`LogicalBlockSize::Lb512`（非 `LBS512`）、`create_from_device(file, uuid)` 需两个参数、分区类型为 `partition_types::BASIC` 常量（无 `Type::from_guid`）。示例代码须锚定 4.1.x。

**同名镜像必须拒绝，不得覆盖。** 旧实现会静默覆盖同名文件，这会导致用户现有镜像中的数据永久丢失。
`create::ensure_target_free` 在任何写入之前检查目标，命中则返回
`already_exists`。注意用 `symlink_metadata`：其他错误（如父目录无权限）要如实上报，
不能当成「不存在」而放行。

## 校验清单（创建后自检）

创建流程结束前应验证：

1. `raw`：偏移 510 处为 `55AA`；
2. `gpt`：**每个**分区起点 1 MiB 对齐（首个必须正好 2048），且未越过可用上界；
3. `mbr`：分区项类型字节与请求一致、起始 LBA 与扇区数一致，末两字节为 `55AA`。
   **分区项数按「主分区数 + 是否启用扩展容器」比对**，不是分区总数——逻辑分区住在
   EBR 里，不在首扇区（`read_mbr_header().used_entries` 只数首扇区）；
4. 按文件系统类型读回校验：
   - FAT32：分区区间内偏移 `+510` 处为 `55AA`，且打开后 `FatType` 确为 FAT32；
   - ext4：分区起点 `+1024+56` 处为超级块魔数 `53EF`（小端）；
   - exFAT：分区起点 `+3` 处为 `EXFAT` 标识。

> **自检流程必须传入真实的分区区间上界**，严禁为图简便而传入 `u64::MAX`：`fscommon::StreamSlice` 按
> `size = end - start` 计算读写窗口，`u64::MAX` 会给出一个远超镜像实际长度的窗口，
> 于是读到的不一定是刚写进去的那一份，校验结果不再可信。
